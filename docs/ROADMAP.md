# 로드맵

현재 단계: 1단계 (Claude Code 런타임)
현재 주차: 1

가정: 퇴근 후와 주말, 주 10~15시간. 0주차 + 1단계 8주 + 2단계 2~3주.

일정이 밀리면 트레이스 뷰 UI, 시나리오 개수, Slack 연동 깊이부터 줄인다.
평가 하네스, 인용 검증, 인젝션 평가는 줄이지 않는다. 이 셋이 하네스 경험의 핵심이다.
2단계가 "나중"으로 밀리지 않게, 1단계가 8주를 넘기면 6~8주차의 서비스 데모와 UI를 줄여서라도 2단계를 시작한다.

# 1단계: Claude Code 런타임 위의 하네스

루프는 Claude Code가 돈다. 우리는 툴, 인용 검증, 가드레일 설정, 평가, 서비스를 만든다.

- [x] Makefile 골격 (`up`, `down`, `capture`, `test`, `eval`, `lock-golden`)
  - [x] `make run` 타깃 (v2 추가, 2주차까지 스텁)
- [x] GOLDEN.lock 생성·검증 스크립트 (labels + snapshots 해시, 불일치 시 평가 거부)
- [ ] `.env.example`을 복사해 `.env` 작성 (1단계는 모델 키 불필요, 비워둔다)
- 완료 기준: `make test`가 빈 테스트로라도 통과하고, GOLDEN.lock 검증 테스트가 있다

## 1주차: 대상 시스템과 시나리오
- [x] 샘플 서비스 2~3개 + Loki + Prometheus를 docker-compose로 기동
- [x] 장애 5종 주입 스크립트: 느린 쿼리, 커넥션 풀 고갈, 잘못된 배포, 외부 API 타임아웃, 메모리 누수 (정의 5개 + `make capture`)
- [x] 시나리오별 정답 라벨 작성 (사람이 직접. AI는 docs/drafts/ 아래에 초안만 제안)
- [x] 시나리오별 스냅샷 캡처 (`make capture`), `make lock-golden`
- 완료 기준: 시나리오 5개가 스냅샷과 라벨을 갖고, GOLDEN.lock이 생성되어 있다

## 2주차: 툴 서버와 Claude Code 러너 v0
- [ ] 데이터 소스 어댑터: 실시간 스택과 스냅샷을 같은 인터페이스로
- [ ] 툴 3개(`search_logs`, `get_metrics`, `get_recent_deploys`)와 MCP 서버(`oncall`). 툴 결과마다 evidence ID를 발급해 서버가 보관
- [ ] 이해 단계: 대화형 Claude Code에 툴 서버를 연결해 시나리오 한 건을 직접 조사시켜 본다. 어떤 툴을 어떤 순서로 부르는지, 어디서 막히는지 메모 (docs/notes/ 아래)
- [ ] `runners/claude_code/`: 격리 실행(빈 임시 디렉터리, `--mcp-config`, 허용 툴 제한, 권한 모드, 시스템 프롬프트는 prompts/ 파일로 주입), stream-json을 RunResult로 정규화. 사용한 플래그는 runners/claude_code/README.md에 기록
- [ ] 한도 측정: 시나리오 한 건을 2~3회 실행하고 실행 전후 구독 한도(`/usage`)를 기록
- 완료 기준: `make run SCENARIO=<id> RUNNER=claude_code`로 리포트, 트레이스, 비용 추정치가 나온다

## 3주차: 평가 하네스와 베이스라인
- [ ] 라벨 로더와 검증: 모르는 키 거부, 카테고리·배포 ID·근거 문자열·메트릭 이름이 시험지에 실제로 있는지 테스트로 확인
- [ ] 시나리오 러너 (시나리오당 3~5회 반복. 2주차 한도 측정 결과에 맞춰 조정)
- [ ] 지표: 원인 카테고리 일치, 핵심 근거 적중, 스텝 수, 비용 추정치, 지연
- [ ] 고정 파이프라인 베이스라인: 조회 순서를 코드로 고정하고, 미리 수집한 데이터를 모델에 한 번에 전달
- [ ] 첫 비교표: 베이스라인 vs Claude Code 런타임(툴 + 프롬프트 v0)
- 완료 기준: `make eval` 한 번으로 비교표가 나온다. 구독 한도 소모량이 기록되어 있다

## 4주차: 툴과 프롬프트 개선
컨텍스트 압축은 이 단계에서 다루지 않는다(Claude Code가 관리). 2단계에서 직접 만든다.
- [ ] 로그 툴이 패턴 집계, 샘플, 상세 조회용 ID를 반환
- [ ] 시스템 프롬프트를 prompts/에서 버전 관리하고, 바꿀 때마다 평가
- [ ] 시나리오를 10개로 확장 (새 라벨은 사람이 작성)
- [ ] v0 → v1 → v2 지표 변화를 기록 (툴 출력과 프롬프트 변경 기준)
- 완료 기준: 버전별 지표 표가 있고, 같은 시나리오의 호출 수나 비용 추정치가 v0 대비 줄었다

## 5주차: 근거 인용과 검증

- [ ] `submit_report` 툴: 제출 시 ID 존재 여부와 발췌문 일치를 서버가 코드로 검증, 실패 시 모델에게 되돌림. 수락된 리포트만 서버가 저장하고 러너가 그것을 읽는다
- [ ] "주장을 근거가 뒷받침하는가"는 LLM 판정을 사람 라벨로 보정
- [ ] 근거가 부족하면 "불확실"로 답하는 동작을 평가에 포함

## 6주차: 서비스 레이어 (데모 수준)

# 2단계: 직접 만든 루프 (2~3주)

같은 저장소에 `runners/own_loop/`를 추가한다. 툴 서버, 시나리오, 평가, 인용 검증은 그대로 재사용한다.

시작 전 준비: Console 가입 → $10~20 선결제(auto-reload 끄기) → 키 발급 → `.env`의 `ONCALL_ANTHROPIC_API_KEY`. 선결제 잔액이 곧 상한이다.

## 2단계 1주: 루프 v0
- [ ] 모델 게이트웨이(`runners/own_loop/gateway`): 재시도, 타임아웃, 토큰·비용 계측
- [ ] 루프 직접 구현: 최대 스텝, 토큰 예산, 시간 상한, 툴 오류 처리
- [ ] 툴 호출 방식 결정(MCP 클라이언트로 같은 서버 호출 vs 함수 직접 호출)하고 결정 기록에 남김
- [ ] 같은 RunResult 형식으로 트레이스 저장
- 완료 기준: `RUNNER=own_loop`로 같은 시나리오가 돈다. 건당 비용을 실측한다

## 2단계 2주: 컨텍스트와 비용
- [ ] 컨텍스트 관리: 오래된 툴 결과 압축, 가설 노트
- [ ] 프롬프트 캐싱, 개발 중 반복은 Haiku, 최종 측정은 Sonnet
- [ ] 3자 비교: 베이스라인 vs Claude Code 런타임 vs 직접 루프 (정확도, 근거 유효율, 비용, 지연, 스텝 수)
- 완료 기준: 3자 비교표와 컨텍스트 전략별 지표 변화

## 2단계 3주 (선택): 마무리
- [ ] 루프 레벨 가드레일(툴 호출 전 검사), 인젝션 평가 재실행
- [ ] 모델 비교(Haiku vs Sonnet)
- [ ] README 비교 섹션: "루프를 직접 만들며 배운 것과 결정"
- 완료 기준: 두 러너를 같은 평가로 비교한 기록
